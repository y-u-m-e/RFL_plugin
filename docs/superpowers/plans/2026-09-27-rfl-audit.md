# RFL Audit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every RFL player's RuneLite client posts its enabled plugins, who it can see, and model-contact events to `yume-api` every 10 s; the API groups them into matches and serves them read-only for rfl.gg.

**Architecture:** The plugin is write-only: small single-purpose classes feed one event queue that `ReportSender` POSTs on a 10 s heartbeat. `yume-api` gets `/plugins/rfl/*` on the existing public host, a new D1 (`RFL_DB`), pure logic in one module (validation, time, corroboration) and D1 work in another.

**Tech Stack:** Java 11, RuneLite client API, injected OkHttp + Gson, JUnit 4 · Cloudflare Workers, D1, Vitest (`@cloudflare/vitest-pool-workers`).

**Spec:** `docs/superpowers/specs/2026-09-25-rfl-audit-design.md` (this repo). Read it before any task.

## Global Constraints

- Two repos. `RFL_plugin` works on `master`. `webpage/apis/yume-api` works on `dev` — **never push `main`**.
- Run `git` / `gradlew` / `npm` / `wrangler` only inside the target repo, never from the workspace root.
- Plugin Hub rules (`.claude/rules/plugin-hub.md`): no reflection, no `new Gson()` (inject `Gson`), no `HttpURLConnection` (inject `OkHttpClient`), no IO on the client thread.
- **Hub rule overrides spec §3 "Config":** third-party HTTP must be opt-in, default off, with the exact warning string `This feature submits your IP address to a 3rd-party server not controlled or verified by RuneLite developers`. So the plugin has exactly one visible setting, `enableReporting` (default `false`), plus hidden `installId`.
- Package `com.rfl`, config group `rfl`. Base URL constant `https://dev-api.ironforged.gg` (switch to `https://api.ironforged.gg` only at release).
- Report interval 10 s. Queue cap 5 min of events. Server: body ≤ 64 KB, `seen` ≤ 100, `events` ≤ 500, strings ≤ 64 chars, `v` must be `1`, one report per `installId` per 5 s → `429`, malformed → `400`.
- Match window 2 min; gap threshold 25 s; install conflict window 25 s; corroboration window ±1200 ms.
- All server times are UTC epoch ms. Event server time = `receivedAt - (sentAt - at)`, clamped to `≤ receivedAt`.
- No banned-plugin logic anywhere in the plugin or API (rfl.gg owns that config).
- D1 caps bound parameters at 100 per statement: pass name lists as one JSON string and use `json_each(?)`, never expand `IN (?, ?, …)`.
- yume-api: bump `version.json` + `package.json` minor, add one bullet to `CHANGELOG.pending.md`, do not cut the changelog.

## Review Focus

1. **RSNs with non-breaking spaces.** RuneLite `Player.getName()` can contain ` `; two clients must emit the identical pair `a`/`b`. Every name goes through `Text.sanitize` before it is used as a key → test in Task 3.
2. **A player leaves view mid-contact** (hop, logout, teleport). The pair must get a `contact_end`, not stay open forever → test in Task 3.
3. **Server rejects a batch.** `400` means it will never succeed: drop it. Network failure, `429`, or `5xx`: requeue. Otherwise one malformed event would block reporting forever → test in Task 5.
4. **Client clock ahead of its own `sentAt`** (`at > sentAt`). Server time must not land in the future → test in Task 7.
5. **Same observer reports the same contact twice** (retry after an ambiguous timeout). Corroboration counts distinct observers, so "seen by" must not inflate → test in Task 9.

**Files:**

**Interfaces:**
- Consumes: `validateReport`, `eventServerTime`, `RFL_LIMITS` (Task 7).
- Produces: `ensureRflTables(db)` (memoized promise, same style as `ensureDropInboxTable`); `handleRflReport(request, env) → { status, body }`.

Schema is spec §5 "`rfl-db` tables" with two pinned additions: `rfl_events.end_at INTEGER` (for `gap`) and `rfl_players.install_id` is the value from the latest report. Indexes: `rfl_events(match_id, type, at)`, `rfl_match_players(rsn)`, `rfl_matches(world, last_active_at)`.

Write order inside `handleRflReport` (decides behavior, keep it):
1. Size check on the raw text (`> 65536` → 400), JSON parse, `validateReport` → 400.
2. Rate limit: `SELECT MAX(last_report_at) FROM rfl_players WHERE install_id = ?`; within 5 s → 429.
3. `install_conflict`: existing `rfl_players` row for this RSN with a different `install_id` and `last_report_at` within 25 s → insert event (`observer_rsn` = rsn, `match_id` null).
4. Snapshot: insert into `rfl_plugin_snapshots` only when the hash of `plugins` differs from `rfl_players.plugin_hash` (hash with `crypto.subtle` SHA-256 over the same `name|source\n` lines as the plugin).
5. Upsert `rfl_players`.
6. If `inPoh`: find the open match (same world, `last_active_at >= receivedAt - 120000`) containing the reporter or anyone in `seen` via `rsn IN (SELECT value FROM json_each(?))`; else create one (`crypto.randomUUID()`). Before updating the reporter's `rfl_match_players` row, if it has `reporting = 1` and `receivedAt - last_at > 25000`, insert a `gap` event (`at = last_at`, `end_at = receivedAt`). Upsert the reporter with `reporting = 1`. Upsert every `seen` RSN (keep `reporting` as is; `max_observers = MAX(existing, number of reporters in this match whose rfl_players.seen_json contains that RSN)`). Set `rfl_matches.last_active_at = receivedAt`.
7. Insert batch events with `at = eventServerTime(...)`, `match_id` = the match from step 6 (null outside a POH).
8. Return `200 { ok: true, matchId }`.
